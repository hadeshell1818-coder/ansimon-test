## 3. AI 위험성평가 초안 흐름 (현재)

1. 담당자가 유해요인을 적는다.
2. AI가 검색어 4~8개를 뽑는다. 일상어와 법령 용어를 섞는다.
3. Supabase 단어 검색으로 법령 최대 12개, 지침 최대 8개를 찾는다.
4. 쓸 만한 근거가 3건 미만이거나 법령이 없으면 외부 공식기관 자료를 검색한다.
5. AI 초안을 만든다. 받은 근거만 인용할 수 있다.
6. 재검토 AI가 초안을 확인한다.
7. 담당자가 확인하고 수정한다.

**단어 검색 순위**
- 단어가 본문에 있으면 +1, 조문 제목에 있으면 +3, 자료 제목에 있으면 +1점이다.
- 두 단어를 함께 검색해서 걸리면 +2점이다.
- 안전보건규칙 총칙(제1~53조)이면 +1점을 더한다.
- 한 자료에서는 최대 3개 조문까지만 고른다.

**의미 검색(임베딩·pgvector)**
- 구현은 되어 있지만 초안에서는 기본으로 꺼 두었다. `SAFETY_SEMANTIC_SEARCH=on`일 때만 쓴다.
- 다음 목표는 "단어 + 의미 + AI 골라내기" 방식이다(`working-rules.md` §2-1).

**재검토로 알게 된 점**: 처음 만든 사례들은 결과가 좋게 나오도록 치우쳐 있었다. 그래서 규칙을 바꿨다.
- 사례는 담당자 말투로 쓴다.
- 검색어는 AI가 뽑는다.
- 기대 근거는 저장소와 상관없이 먼저 정한다.
- 결과는 "자료 없음"과 "있는데 못 찾음"으로 나눈다.

## 6. 틀렸던 것과 고친 방법

| 문제 | 원인 | 해결 |
|---|---|---|
| SQL Editor에서 `syntax error at "<!"` | 복사용 HTML 페이지를 통째로 붙여넣음 | `.sql` 파일을 미리보기로 바로 보내 복사하게 함 |
| KOSHA 목차와 본문 제목이 섞임 | 제목이 여러 줄로 나뉨, 본문 속 `[별표 4]` 인용 | "2. 적용범위"를 기준점으로 잡고, 부록 제목은 마지막 목차 뒤에서만 인정 |
| 그림 PDF를 OCR로 읽었더니 숫자가 틀림 | 230mm가 2300001로 읽힘 | OCR을 쓰지 않고 화면을 보고 옮겨 적은 뒤 "원문 확인" 표시 |
| PL/pgSQL 트리거 오류 | 함수 하나가 두 테이블의 칸을 참조 | 함수를 두 개로 분리 |
| 의미 검색을 넣었더니 정확도가 떨어짐(84 → 74) | 엉뚱한 후보가 단어 검색 결과를 밀어냄 | 단어 검색 결과는 유지하고 덧붙이는 방식으로 바꿈. 이어서 초안에서 기본으로 끔. 다음은 AI 골라내기 |
| 시뮬레이션 점수가 실제보다 높게 나옴 | 사례 작성 방식이 치우침 | 작성 규칙을 정하고, 재검토를 기본 단계로 넣음 |
| 클라우드 환경에서 OpenAI·운영 주소·안드로이드 도구 접속 차단 | 네트워크 정책 | APK는 GitHub Actions에서 빌드. AI 채점은 환경 설정이 끝나면 직접 실행(`todo.md` 1-0) |

## 7. 다른 앱을 만들 때 그대로 쓸 원칙

1. **AI는 초안만 만든다.** 확정·발송은 사람이 하고, 원본·AI 제안·사람의 수정·승인 시각을 모두 남긴다.
2. **근거는 저장소에서 받은 것만 인용한다.** 근거가 없으면 "근거 미확인"으로 표시하고 자동 저장하지 않는다.
3. **실패를 숨기지 않는다.** 연결 실패, 검색 실패, AI 형식 오류를 각각 구분해서 보여준다. 결과 없음과 실패는 다르다.
4. **상태를 섞지 않는다.** 발송 시도, 수신, 확인, 조치 완료는 각각 다른 상태다.
5. **근거 검색은 일반적인 방식을 따른다.** 검색어 바꾸기 → 단어+의미 후보 → AI 골라내기 → 인용 초안 → 재검토. 시험 사례에 맞춰 관련어를 하나씩 넣지 않는다.
6. **시뮬레이션은 문제를 찾는 도구다.** 현실과 같은 조건으로 만들고, 결과를 재검토하고, 나쁜 결과도 보고한다.
7. **자료는 출처·버전과 함께 넣는다.** 넣은 버전을 기록하고, 정기적으로 개정 여부를 비교한다. 그림 자료는 OCR 대신 사람이 옮겨 적고 표시한다.
8. **비밀값은 환경 설정에만 둔다.** 대화, 코드, HTML에 넣지 않는다.
9. **변경마다 시험을 돌린다.** 시험 통과 → PR → 병합. 확인하지 않은 것(운영 반영, 실기기, 실제 AI 응답)은 완료라고 쓰지 않는다.
10. **작업 방식도 문서로 남긴다.** 규칙(`working-rules.md`), 할 일(`todo.md`), 과정(이 파일)을 두고, 작업을 시작하기 전에 읽는다.

## 9. 이후 기록

- 2026-11-01 근거 골라내기(재순위) 단계를 `recommendRisk`에 추가했다(`SAFETY_EVIDENCE_MODE=words|meaning|rerank`, 기본 words). 초안 단위 채점 도구 `scripts/simulate-drafts.cjs`와 담당자 말투 사례 59유형 236건(A·B 세트)을 만들었다. 기대 근거 정규식을 오프라인 SQL로 대조했더니 너무 느슨해서 엉뚱한 조문도 정답으로 치는 항목이 있었다(예: "온도"가 건조설비 조문에 걸림). 그래서 조문 제목 단위로 좁혔다. 자료 보완은 사용자가 정리한 산업안전보건 법령 체계(법·시행령·시행규칙 → 안전보건규칙·취업제한규칙 → 고시·예규·훈령 → 공단 기술상의 지침·작업환경표준·KOSHA GUIDE) 기준으로 분류한다.
- 2026-11-01 클라우드 환경 비밀값은 Network secrets(프록시가 키를 붙임)에 두고, 코드 쪽 키 칸에는 `proxy`를 넣는 방식으로 연결했다. Node fetch는 `NODE_USE_ENV_PROXY=1`이 있어야 프록시를 거친다. 날짜가 11월로 넘어가면서 실패하던 테스트(위험성평가 엑셀 출력 기간)를 오늘 날짜 기준으로 고쳤다.
- 2026-11-01 초안 시뮬레이션 1·2차(A세트 354+351건, B세트 236건)를 돌렸다. 검색어에 법령 용어가 든 비율이 28%였는데, 지시문을 고쳐 65%로 올렸다. 골라내기는 후보 4.5개만 남길 만큼 엄격해서 완화했다(7.4개). B세트 검증 결과, 목표 방식(단어+의미+골라내기)이 단어 검색만 쓸 때보다 후보 49→64%, 최종 인용 9→14%로 나았다. 다만 절대 수준이 낮아 운영 적용은 보류했다.
- 2026-11-01 검색 버그 세 가지를 찾았다. ① Supabase ilike가 결과를 순서 없이 30건에서 잘라 법령 조문이 빠졌다 → 법령 전용 검색을 추가했다. ② "안전조치·점검" 같은 흔한 단어가 점수를 독차지했다 → 드문 단어 가중치(IDF)와 일반어 제외를 넣었다(A 58→62%, B 58→61%). ③ 의미 검색 함수가 요청이 몰리면 시간 초과로 조용히 실패했다(실행의 17~25%) → 007 SQL로 색인을 타게 고쳤다. 검색어 다듬기(일반어를 문장 맥락으로 교체)는 효과가 작아(+0~2%p) 기본값을 꺼 두었다.
- 2026-11-01 RAG 표준 단계(① 입력 이해 ~ ⑦ 평가)를 중심 틀로 정하고 ②→③→⑤→⑥ 순서로 검증하기로 했다(working-rules §2-2). 장흥 평가서·우체국 점검표 429항목으로 15개 공정별 사례 120건(A·B 말투, gpt-4.1 작성)을 만들었다. 점검 항목이 후보에 오르는 비율은 13~31%였다. 원인은 검색어 부족이 아니라(검색어가 정답 항목 본문에 있는 경우 93%) 가져오는 단계의 잘림이었다. 자료 전체를 대상으로 순위를 매기면 상위 40개 안 비율이 15~20%에서 38~49%로 올랐다. 직접 적용되는 법령이 상위 6개 안에 있는 비율은 62~71%였고, 집배 공정이 0~13%로 가장 낮았다(이륜차 자료 부족).
