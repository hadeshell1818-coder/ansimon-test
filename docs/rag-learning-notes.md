# RAG 근거 검색 개선 학습 노트 (2026-10-31 ~ 11-02)

안심ON 위험성평가의 AI 초안이 **담당자가 어떤 말투로 쓰든 맞는 근거(법령·KOSHA 지침·우체국 점검표·사고사례)와 개선대책을 찾게** 만든 과정을 공부용으로 정리했다. 무엇이 문제였고, 무엇을 시도했고, 어떤 것이 효과가 있었는지, 어떤 프로그램을 썼는지를 순서대로 적었다.

자세한 측정 기록은 `docs/evidence-simulation-2026-11.md`, 날짜별 개발 기록은 `docs/dev-history.md`, 작업 규칙은 `docs/working-rules.md` §2-1·§2-2에 있다.

## 1. RAG란, 그리고 이 앱의 RAG

**RAG(Retrieval-Augmented Generation, 검색 증강 생성)**: AI가 기억만으로 답하지 않고, 먼저 자료를 검색해서 찾은 자료를 보면서 답을 쓰게 하는 방식이다. 근거를 꾸며내는 일(환각)을 줄이고 출처를 남길 수 있다.

이 앱에서는 아래 순서로 동작한다. 표준 RAG 단계 ①~⑦에 맞춰 검증했다(사용자 합의, working-rules §2-2).

```text
담당자 입력: 유해·위험요인 글 + 공정 + (사진)
   │
① 입력 이해 ── AI(gpt-4.1-mini)가 글·사진을 읽고
   │            · "이해한 위험" 한 문장
   │            · 검색어 5~8개(현장 말 + 법령 용어 + 설비 이름 다른 표기)
   │
② 후보 검색 ── 동시에 세 가지
   │            · 단어 검색: Supabase 안에서 순위(008 SQL, 드문 단어 가중치)
   │            · 의미 검색: 임베딩 벡터(006·007 SQL) + HyDE(법령 문체 가상 문장)
   │            · 사고사례 검색(승인된 사례가 있을 때만)
   │            → 후보 약 50개
   │
③ 재순위 ──── Cohere Rerank API가 "이해한 위험"과 후보를 비교해 순서를 다시 정함
   │            → 종류와 상관없이 상위 10개
   │
④ 초안 ────── AI가 근거 10개를 보고 개선대책 5개를 쓰고, 대책마다 뒷받침 근거(refs)를 단다
   │
⑤ 자동 검증 ── AI가 대책마다 "이 위험을 논리적으로 줄이는가", "붙은 근거가 뒷받침하는가"만 번호로 답함
   │
⑥ 사람 확인 ── 화면: AI가 이해한 위험 / 개선대책(문장만) / 관련근거(내용 이름) / 근거 순위 / 소요 시간
   │            담당자가 필요 없는 대책을 지우고 고친다
   │
⑦ 평가 ────── 시뮬레이션(로컬 도구)과 운영 「검색 정확도 점검」 버튼으로 측정
```

코드 위치는 거의 전부 `safety-knowledge.cjs`의 `recommendRisk()` 안이다(7절 참고).

### 1-1. 임베딩 검색 기초 (기본 RAG)

임베딩은 글의 뜻을 숫자 목록(벡터)으로 바꾸는 것이다. 뜻이 비슷한 글은 벡터도 가깝다. 임베딩은 두 번 쓰인다.

```text
[미리 한 번: 색인] — 자료를 추가·수정할 때만 다시
자료(법령·지침·점검표) → 조문·항목 단위로 나누기(청킹) → 임베딩 ① → 벡터 저장소(Supabase pgvector, HNSW 색인)

[질문할 때마다: 검색]
유해·위험요인 글 → 임베딩 ② → 저장된 벡터와 가까운 것 찾기(코사인 거리) → 후보 → AI가 후보를 읽고 초안 작성
```

- **엔진**: OpenAI `text-embedding-3-small`(1536차원). 2026-11-02 기준 조문 7,675개 전부 이 엔진으로 색인됨. 근거자료실 「의미 검색 색인 만들기」 버튼이 ①을 한다.
- **같은 엔진 규칙**: ①과 ②는 반드시 같은 엔진이어야 비교가 맞다. 엔진을 바꾸면(`SAFETY_EMBEDDING_MODEL`) ①을 전부 다시 하고, 차원이 다르면(예: bge-m3 1024차원) 표의 벡터 칸 크기도 바꾼다.
- **청킹**: 법령은 "제N조", KOSHA 지침은 "4.2 제목", 점검표는 "항목" 단위로 나눴다. 너무 크면 엉뚱한 내용이 섞이고, 너무 작으면 맥락이 끊긴다.
- **비용·시간**: ②는 초안 한 건에 한 번, 약 0.3~0.6초, 1원 미만. 단어 검색과 동시에 돈다.

### 1-2. 이 앱은 "고급 RAG"(Advanced RAG)

기본 RAG(임베딩 검색 → AI 답변)만으로는 맞는 근거를 자주 놓쳐서, 실무에서 많이 쓰는 보강 세 가지를 더했다.

```text
유해요인 글 ─┬─ 단어 검색(DB 안 순위·드문 단어 가중치) ─────────┐
             └─ HyDE 가상 문장 → 임베딩 ② → 의미 검색 ──────────┴→ 후보 약 50개 → Cohere 재순위 → 상위 10개 → AI 초안
```

| 보강 | 하는 일 | 왜 필요했나 |
|---|---|---|
| 하이브리드 검색 | 단어 검색과 임베딩 검색을 함께 돌려 후보를 합침 | 임베딩은 뜻은 잘 잡지만 "롤파렛트" 같은 정확한 이름을 놓치고, 단어 검색은 그 반대 |
| HyDE | 질문 대신 AI가 쓴 "법령 문체 가상 문장"을 임베딩 | 직원 말투("자빠질뻔")와 법령 말투("전도의 방지")가 달라 벡터가 멀어서 |
| 재순위 | 후보를 질문과 하나씩 같이 읽고 관련도 순서를 다시 매김 | 임베딩 검색은 순서가 거칠어 맞는 근거가 뒤로 밀림(상위 4개 적중 70·79% → 90·87%) |

## 2. 단계별로 무엇을 했나 (문제 → 원인 → 해결 → 결과)

### ① 입력 이해: 담당자 말을 검색할 수 있는 말로 바꾸기

| 문제 | 원인 | 해결 | 결과 |
|---|---|---|---|
| "넘어질 뻔" → "제3조(전도의 방지)"를 못 찾음 | 현장 말과 법령 말이 다름 | 검색어 지시문에 "절반 이상은 법령 용어로" + 분류표(넘어짐→전도의 방지, 끼임→회전축·덮개 등) | 법령 용어 포함 28% → 65% |
| "롤파렛트"로 쓰면 점검표 "롤파레트·롤테이너"를 못 찾음 | 같은 설비를 현장마다 다르게 씀 | `SPELLING_GROUPS`: 다른 표기를 함께 검색(지게차↔포크리프트, 오토바이↔이륜차 등) | 롤파렛트 사례 정답 항목 찾음 |
| AI가 검색어에서 "계단"을 빠뜨림 | AI가 법령 용어 위주로만 씀 | "설명에 나온 설비·장소 이름은 빠짐없이 그대로" 지시 | 계단 근거가 잡힘 |
| "이거 위험해 보임" + 사진이면 순위가 빗나감 | 순위·검증 단계는 글만 봤음 | AI가 "이해한 위험" 한 문장을 쓰고 순위·의미 검색·검증에 사용 | 파손 가로등 사진 → "전선 노출" 인식 |
| 설비 이름이 있는데 "어느 부위인가요?" 질문 | 질문 판단이 너무 민감 | 설명에 설비 이름이 있으면 세부 질문 생략 | 질문 없이 바로 초안 |

배운 점: 검색 품질의 출발점은 **검색어**다. 사용자의 말을 그대로 쓰지 말고, 자료에 실제로 쓰인 말로 바꿔 주는 단계(query rewriting / query expansion)가 필요하다.

### ② 후보 검색: 맞는 자료를 후보 안에 넣기

#### 단어 검색

| 문제 | 원인 | 해결 |
|---|---|---|
| 법령 조문이 후보에서 통째로 빠짐 | Supabase `ilike` 검색이 결과를 순서 없이 30건에서 자름. "바닥"처럼 수백 곳에 나오는 단어면 정답이 잘려 나감 | 조문 제목 검색, 두 단어 동시 검색, 법령 전용 검색 → 최종적으로 **DB 안에서 전체에 점수를 매겨 상위만 받는 함수**(`supabase/008_ranked_word_search.sql`) |
| "안전조치·점검" 같은 흔한 단어가 점수를 독차지 | 모든 단어를 같은 무게로 셈 | **IDF(드문 단어 가중치)**: `1 + ln((전체+1)/(포함 조문 수+1))`. 일반어 목록(`GENERIC_TERMS`) 제외 |
| "사용"(2,473/7,675곳) 같은 말이 검색을 느리게 함 | 흔한 말일수록 DB가 점수 매길 행이 많아짐 | 전체 조문의 20%를 넘게 나오는 말은 순위 검색에서 뺌 |
| 일반 사업장 조문(제3조 전도 등)이 건설·갱내 장 조문에 밀림 | 같은 단어가 여러 장에 나옴 | 안전보건규칙 총칙(제1~53조) +1 가산(여러 조합을 비교해 이것만 두 세트 모두에서 올랐음) |
| 점검표 항목이 한 문서에서 3개까지만 들어감 | 문서당 개수 제한 | 점검표는 공정 단위로 제한 |

결과: 64건 기준 67% → 92%, 111건 기준 55% → 91%. 섹터 시뮬레이션에서는 검색어가 정답 본문에 있는 경우가 93%인데 후보에 들어간 건 18%였다. **원인은 검색어가 아니라 가져오는 단계의 잘림**이었고, 008 SQL로 해결했다.

#### 의미 검색(벡터 검색)

- 조문마다 뜻을 숫자 벡터(임베딩, `text-embedding-3-small` 1536차원)로 저장하고, 질문과 뜻이 가까운 조문을 찾는다(`supabase/006_semantic_search.sql`, pgvector).
- 요청이 몰리면 시간 초과(57014)로 조용히 실패했다. 벡터 색인(HNSW)을 먼저 타도록 함수를 고쳤다(`007_semantic_search_speed.sql`).
- **HyDE(Hypothetical Document Embeddings)**: 질문을 그대로 검색하지 않고 AI가 "법령이라면 이렇게 썼을 것" 같은 가상 문장을 만들어 그 문장으로 검색한다. 후보 안 정답 72·73% → 79·77%.
- **실패한 시도**: 단어 검색과 의미 검색 순위를 섞는 RRF(Reciprocal Rank Fusion)는 운영 점검에서 84/95 → 74/95로 오히려 나빠졌다. 의미 검색이 "비슷하지만 핵심이 아닌" 조문을 올렸기 때문이다. 단어 검색 결과는 그대로 두고 의미 검색만 찾은 것을 덧붙이는 방식으로 바꿨고, 지금은 재순위가 최종 순서를 정한다.

배운 점: 단어 검색과 의미 검색은 서로 다른 실수를 한다. **둘 다 넓게 후보를 모으고, 순서는 재순위 모델에 맡기는 것**이 표준 방식이다.

### ③ 재순위: 후보 50개 중 진짜 맞는 것을 위로

| 시도 | 상위 4개 안 맞는 근거(A·B) | 시간 | 판단 |
|---|---|---|---|
| 검색 순서 그대로 | 70% · 79% | - | 기준점 |
| GPT(gpt-4.1-mini)에게 고르게 함 | 상위 10개 56~57% → 47~50%로 오히려 하락 | 수 초 | 폐기: 정답을 버림 |
| bge-reranker-v2-m3(허깅페이스, ONNX로 직접 실행) | 91% · 89% | CPU에서 사례당 약 56초 | 정확하지만 느리고 서버비 듦 |
| **Cohere rerank-v3.5(호스팅 API)** | **90% · 87%** | **0.3~0.6초** | **채택** |

- 공정하게 비교하려고 후보 50개를 파일로 저장해 두고(`--dump-pool`), 후보 전체를 판정 AI로 **한 번만** 채점한 뒤 순서만 바꿔 가며 비교했다(`scripts/rerank-eval.cjs`).
- Cohere 점수를 절대 기준(예: 0.1 이상만)으로 쓰려 했지만, 정답 중앙값 0.096·오답 0.077로 겹쳐서 쓸 수 없었다. **순서만 믿는다.**
- 법령 6 + 지침 4처럼 자리를 나누는 것보다 종류 구분 없는 상위 10개가 같은 수준(95% vs 94%)이었고, 맞는 법령이 없을 때 엉뚱한 법령이 자리를 채우는 문제가 없어 이쪽을 택했다.
- Cohere가 실패하거나 3초를 넘기면 검색 순서로 초안을 만들고, 화면에 "근거 순위: …"로 사유를 표시한다.

배운 점: "고르는 일"은 범용 대화 AI보다 **전용 재순위 모델(cross-encoder)**이 훨씬 잘하고 싸고 빠르다.

### ④ 초안: 대책과 근거를 짝지어 쓰기

- 문제: 계단 미끄럼 대책(미끄럼 방지 매트) 옆에 "제26조(계단의 강도)"가 붙었다. 근거를 초안 전체에 붙이고 화면에는 법령만 골라 보여 줬기 때문이다.
- 해결: 대책마다 그 대책을 실제로 뒷받침하는 근거만 refs로 단다(`{text, refs}`). 점검표·KOSHA 지침·사고사례도 근거로 인정한다.
- 대책은 기본 5개다. 담당자가 필요 없는 것을 지우는 편이 낫다(사용자 결정).
- 초안이 근거를 하나도 달지 않는 경우가 가끔 있다(지게차 4번 중 1번). 그때는 전달된 근거를 검증 단계에 넘겨 대책별로 고르게 한다.

### ⑤ 자동 검증: 가볍게

- 처음에는 검토 AI가 대책 5개와 요약을 처음부터 다시 썼다(4~5.6초). 그러면서 교육·점검 같은 일반 대책을 지워 3~4개만 남기기도 했다.
- 지금(사용자 결정): 대책마다 두 가지만 번호로 답한다. ① 이 위험을 논리적으로 줄이는가 ② 붙은 근거가 그 대책을 뒷받침하는가. 대책 문장은 다시 쓰지 않는다.
- 결과: 검토 평균 2.1초. 9건 측정에서 뺀 근거 0건, 대책 2건이었다.

배운 점: AI 호출 시간은 대부분 **AI가 쓰는 글의 양(출력 토큰)**에 비례한다. 검증 단계는 "판정만" 하게 하면 빨라진다.

### ⑥ 사람 확인 화면

- 개선대책 칸: 대책 문장만 넣는다. "(근거 1)" 같은 표시는 평가표·엑셀에 섞여서 지웠다.
- 관련근거 칸: 자료가 **무엇을 말하는지** 쓴다. "…검색자료 우편작업 · 접수작업 · 항목 5" 같은 저장 위치를 "우체국 작업 위험요인 점검표(접수작업): 파렛트 파손·이동·날카로운 강선"처럼 바꿨다. 같은 내용의 점검표 항목은 한 줄로 합친다.
- "AI가 이해한 위험" 한 줄: AI가 제대로 알아들었는지 담당자가 바로 확인한다(평가표에는 저장하지 않음).
- 단계 표시: 서버의 실제 단계(위험 이해 → 근거 찾기 → 초안 작성 → 검토)와 경과 초를 보여 준다. 끝나면 단계별 소요 시간을 보여 준다.

### ⑦ 평가: 어떻게 쟀나

- **사례 세트**: 담당자 말투 59유형 236건(A·B 두 세트, `seed-assets/draft-simulation-cases.json`), 장흥 평가서·점검표 429항목으로 만든 15개 공정 120건(gpt-4.1이 작성, 로컬만), 운영 점검용 175건(`seed-assets/search-evaluation-cases.json`).
- **채점 기준**: 처음에는 "기대 조문과 정확히 일치"만 맞음으로 쳤더니 너무 엄격했다. "기대 근거와 일치하거나, 판정 AI가 직접 적용된다고 본 근거"로 바로잡았다. 판정 AI 오차는 ±5%p 정도로 본다.
- **결과를 두 갈래로 나눔**: "자료 없음"(→ 추가할 자료 목록)과 "자료는 있는데 못 찾음"(→ 검색 개선).
- **운영 점검**: 근거자료실 「검색 정확도 점검」 버튼이 175건으로 단어 검색·의미 검색 방식을 운영 자료로 비교한다.

## 3. 시간 단축 과정

| 단계 | 시간(이 환경) | 바꾼 것 |
|---|---|---|
| 시작(사용자 점검) | 질문 1회 + 약 30초 | - |
| 단계 동시 실행 | 약 24초 | 단어·의미(HyDE)·사례 검색을 차례 실행 → 동시 실행 |
| 사례 검색 생략·캐시 | 약 17.9초 | 승인 사고사례가 0건이면 사례 검색 생략, 승인 문서 목록 10분·단어 빈도 6시간 캐시 |
| 왕복 줄이기 | 약 16초 | 문서 목록·전체 조문 수·단어 빈도를 한 번에 동시 조회, 다른 표기는 원래 단어 빈도 공유, 흔한 말 제외, 설비가 있으면 질문 생략 |
| 가벼운 검토 | **평균 13.6초**(10.8~17.4초, 13건) | 검토가 번호로만 답함(4~5.6초 → 약 2초) |

지금의 시간 구성(한 건 예시): 위험 이해 1~2초 → 근거 찾기 4~5초(Cohere 0.4초 포함) → 초안 작성 5~6초 → 검토 약 2초.

배운 점:
- **서로 기다릴 필요 없는 일은 동시에** 돌린다(`Promise.all`).
- 외부 DB 왕복 1번이 약 1초다(이 환경 기준). **왕복 횟수를 줄이는 것**이 쿼리를 빠르게 하는 것보다 효과가 크다.
- 잘 안 바뀌는 값(문서 목록, 단어 빈도)은 **캐시**한다. 대신 적재·승인 때 캐시를 비운다.
- 남은 큰 시간은 AI가 글을 쓰는 시간(초안)이다. 단계 표시로 기다림을 덜 답답하게 했다.

## 5. 실패와 교훈

1. **측정이 운영을 망칠 수 있다.** 시뮬레이션이 동시에 많은 요청을 보내 운영 화면이 Supabase 시간 초과(57014)를 맞았다. 동시 실행 수를 줄이고, 읽기 요청 1회 재시도와 캐시를 넣었다.
2. **색인이 오래되면 측정이 틀린다.** 자료를 올린 뒤 검색 색인을 다시 만들지 않고 측정해서 결과가 틀렸다.
3. **채점 기준이 결과를 좌우한다.** 너무 엄격해도(정확한 항목 일치), 너무 느슨해도("온도"가 건조설비 조문에 걸림) 틀린 결론이 나온다.
4. **AI로 고르기 < 전용 재순위 모델.** GPT 골라내기는 정답을 버렸다.
5. **순위 섞기(RRF)가 항상 낫지는 않다.** 직접 재 보고 정한다.
6. **점수 절대값은 기준으로 못 쓴다.** 재순위 점수는 순서로만 쓴다.
7. **에이전트(AI)가 쓴 시험 문장은 너무 깔끔하다.** 표기 차이(롤파렛트/롤파레트)를 담지 못해 실제 사용자 점검에서 처음 드러났다. 실제 직원 문장으로 꼭 다시 확인한다(working-rules §3).
8. **근거는 대책 단위로 붙인다.** 초안 전체에 붙이면 엉뚱한 연결이 생긴다.
9. **화면에는 사람이 읽는 말을 쓴다.** 저장 위치("항목 5")나 내부 번호는 보이지 않게 한다.
10. **검증 단계가 원본을 다시 쓰면 의도와 어긋난다.** 검토가 일반 대책을 지워 버렸다. 검증은 판정만 하게 한다.

## 8. 다른 앱을 만든다면 (권장 순서)

1. **자료부터 확인한다.** 찾을 자료가 저장소에 없으면 검색을 아무리 고쳐도 소용없다. "자료 없음"과 "못 찾음"을 나눠 센다.
2. **평가 세트를 먼저 만든다.** 실제 사용자 문장(오탈자·줄임말·다른 표기 포함)과 기대 근거를 정하고, 기대 근거는 저장소와 상관없이 정한다.
3. **검색어를 자료의 말로 바꾼다.** 현장 말 + 전문 용어 + 다른 표기.
4. **후보는 넓게 모은다.** 단어 검색(DB 안 순위, IDF) + 의미 검색(임베딩 + HyDE). 잘림이 없는지 확인한다.
5. **순서는 전용 재순위 모델에 맡긴다.** 호스팅 API가 비용·속도 면에서 유리했다.
6. **근거는 답의 단위(대책)마다 붙이고, 화면에는 사람이 읽는 이름으로 보여 준다.**
7. **검증은 판정만 하게 해서 가볍게.**
8. **단계 표시와 소요 시간을 처음부터 넣는다.** 운영에서 실제 시간을 알 수 있다.
9. **측정은 운영과 분리한다.** 동시 요청 수를 제한하고, 측정 도구는 중단 후 이어서 돌 수 있게 만든다.

## 9. 더 공부할 키워드

- **BM25 / TF-IDF**: 단어 검색 점수의 표준. 이 앱의 IDF 가중치가 그 일부다.
- **임베딩, 벡터 검색, pgvector, HNSW 색인**: 의미 검색의 원리와 속도.
- **Query rewriting / Query expansion**: 검색어 다시 쓰기, 동의어·다른 표기 넓히기.
- **HyDE(Hypothetical Document Embeddings)**: 가상 답변 문장으로 검색하기.
- **Hybrid search, RRF(Reciprocal Rank Fusion)**: 단어·의미 검색 결과 합치기.
- **Cross-encoder reranker(bge-reranker, Cohere Rerank)**: 질문과 문서를 함께 읽고 관련도를 매기는 모델. 처음 검색에 쓰는 bi-encoder(임베딩)와의 차이.
- **Recall@k / Precision@k**: "상위 k개 안에 정답이 있는 비율"(이 노트의 "상위 4개 안 맞는 근거").
- **LLM-as-a-judge**: AI로 채점하기. 판정 오차와 편향을 감안해야 한다.
- **Grounding / Citation**: 답의 각 부분을 근거와 연결하기(이 앱의 대책별 refs).
- **Latency budget**: 단계별 시간 예산, 병렬화, 캐시, 출력 토큰 줄이기.
