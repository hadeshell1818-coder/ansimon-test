# 산업안전보건 관리: 현재 구현과 Supabase 구성

## 화면

기존 /risk.html을 확장한다. 직원 신고·알림·귀국보고는 변경하지 않는다.

| 탭 | 현재 상태 |
|---|---|
| 내부위험 접수 | 기존 신고 대기함 유지. 담당자가 위험성평가 등록을 누르면 같은 사진을 평가표로 연결 |
| 위험성평가표 | 첨부 우체국 양식의 핵심 순서 반영: 작업·유해위험요인·현재조치·가능성·중대성·위험성·허용여부·감소대책·담당자·개선기한 |
| 근거자료실 | 공개 출처 목록 조회·검색·등록. 평가 상세에서 작업·위험요인으로 관련 자료를 검색하고 선택 연결 |

개선완료 사진과 이행결과는 위험성평가 상세 흐름 안에서 처리한다. 다른 산업안전 분야 탭은 우체국 정기 보고양식과 내부 자료를 확인한 뒤 추가한다.

## 새 Supabase 프로젝트 연결

1. 기관 정책상 외부 클라우드 사용이 허용되는지 확인한다. 현재 범위는 공개 출처 메타데이터만이다.
2. Supabase 계정에서 새 프로젝트를 만든다. 비용이 발생하는 플랜은 별도 승인 후 선택한다.
3. 프로젝트 SQL Editor에서 `supabase/001_safety_knowledge.sql`을 한 번 실행한다. 기존 프로젝트에 덮어쓰는 마이그레이션이 아니다.
4. 서버 환경변수에 `SAFETY_SUPABASE_URL`과 `SAFETY_SUPABASE_SERVICE_KEY`를 설정한다. URL은 프로젝트 URL, 키는 서버용 secret/service_role 키다. 공개 anon 키로는 접근할 수 없다. 키를 HTML·Git·대화에 넣지 않는다.
5. 서버를 재시작하고 안전관리담당자로 /risk.html에 로그인한다.
6. 근거자료실에서 연결 상태 확인 후 '기본 출처 목록 등록'을 누른다. 공개 출처 7건만 등록한다. 반복 실행은 source_url 기준 중복을 건너뛰며 기존 검토 결과를 덮어쓰지 않는다.
7. Supabase Table Editor의 safety_documents와 화면에서 등록 여부를 확인한다.

현재 서버는 .env를 자동으로 읽지 않는다. 배포 환경변수를 쓰거나 로컬에서 Node의 `--env-file=.env` 옵션을 사용한다. 기존 SUPABASE_KEY/RA_SOURCE는 과거 빈도 계산용이므로 이번 자료실과 혼용하지 않는다.

## 지금 만드는 테이블

- safety_documents: 자료 제목, 공식 출처, 기관, 분야, 자료종류, 작업·위험 태그, 국가, 이용조건, 검토상태, 적용기간, 버전, 검토자.
- safety_document_sections: 향후 허가된 본문을 조항·사례·점검항목 단위로 저장. 문서/버전/원문 위치/해시를 보존한다. 승인 및 본문 이용 허용 전 입력을 차단한다.
- safety_assessment_evidence: 위험성평가 ID와 검토한 문서·본문 위치를 연결한다. 평가 시점의 근거를 나중에 개정자료로 바꾸지 않는다.

브라우저 anon/authenticated 권한은 차단하고 RLS를 활성화한다. 현행 앱의 세션은 Supabase Auth가 아니다. 서버가 기존 안전관리담당자 권한을 검증한 후 서비스 키를 사용한다. 서비스 키는 RLS를 우회하므로 서버 검증이 필수다. 이번에는 공개 메타데이터만 수용하며 기관별 비공개 자료를 혼합하지 않는다.

초기 목록은 링크 후보일 뿐, 본문 적재·AI 근거검색 완료가 아니다. SIF는 변경금지 조건, 해외 자료는 국내 법적 의무와의 차이를 명시한다. 법령 검색 페이지는 개별 현행 조항의 근거를 대신하지 않는다.

## 다음 단계의 관계 모델 (아직 미구현)

기관/작업/장비 → 승인된 점검표 버전 → 점검항목 → 점검결과 → 위험성평가 → 개선조치 → 완료 검증.

점검항목과 평가 근거에는 문서 전체가 아닌 safety_document_sections의 고정 버전을 연결한다. 다대다 evidence_links에 인용 위치, 사용 당시 검토자와 시점을 남긴다. 과거 평가의 근거를 새 개정본으로 조용히 바꾸지 않는다.

작업장 점검과 건강정보는 별도 권한·저장영역으로 분리한다. 신규 업무 테이블을 만들기 전에 기존 JSON 신고·평가 ID와 이관 계획을 확정한다. 현재 업무 데이터는 Supabase로 이관하지 않는다.

## 자료 누적 절차

출처 등록 → 이용조건·최신성·현장 적합성 검토 → 승인 → 허용된 원문만 비공개 Storage 보관 → 텍스트/표 추출 → 조항/사례 분할 → 키워드 검색 → 필요 시 벡터 검색 → 근거 표시 → 담당자 확정.

Storage 버킷, 자동 수집, 본문 추출, 벡터 생성, 법령 갱신 감시, AI 답변 연결은 이번 변경에 포함하지 않는다. 파일을 저장했다고 AI가 자동 학습하지 않는다. 승인 취소·개정 자료는 검색 시 제외하되 과거 평가 근거 이력은 보존한다.

## 검증과 배포

실제 프로젝트 생성·SQL 적용·적재는 연결 정보가 마련된 뒤 별도로 확인해야 한다. SQL 적용 전 화면은 '미연결' 또는 연결 오류를 표시한다. 기록 쓰기 실패를 성공으로 처리하지 않는다. 이번 변경은 GitHub 자동 push나 배포를 수행하지 않는다.
