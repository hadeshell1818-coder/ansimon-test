# 작업 규칙 (모든 작업 시작 전에 읽는다)

AGENTS.md와 함께 적용한다. 사용자와 합의한 운영 규칙이며, 바뀌면 이 파일을 먼저 고친다.

## 1. 결과 재검토는 기본 단계

모든 시뮬레이션·분석·개선 결과는 보고하기 전에 다시 검토한다.

- **측정이 목적을 재는가**: 방법 자체가 결과를 미리 정하지 않았는지 확인한다(예: 기대 근거를 이미 올린 자료에서 고르면 "자료 있음 100%"는 당연하다).
- **편향 점검**: 사례 문장에 법령 용어를 미리 넣었는지, 검색어를 사람이 대신 정했는지, 그래서 실제보다 좋게 나왔는지 본다.
- **숫자 재확인**: 분모·분자, 세트 이름, 이전 결과와의 비교를 다시 계산한다.
- **교차 확인**: 검색·순위 변경은 사례 세트 2개 이상에서 재고, 한 세트라도 떨어지면 채택하지 않거나 그 사실을 함께 보고한다.
- **나쁜 결과도 보고**: 효과가 없거나 나빠진 시도, 측정의 한계, 확인하지 못한 부분을 숨기지 않는다.

## 2. 위험성평가 근거 시뮬레이션의 목적

시뮬레이션은 점수를 올리는 작업이 아니라, 실제 운영(담당자가 유해요인을 적고 AI가 근거를 찾아 초안을 쓰는 과정)에서 생길 문제를 시범운영 전에 **드러내서 미리 해결**하는 작업이다. 놓친 근거·엉뚱한 인용·자료 없음은 실패가 아니라 찾아낸 문제로 다루고, 결과를 좋게 보이려고 사례·검색어를 손보지 않는다. 조건은 현실과 같게(담당자 말투, AI 검색어, 운영 자료, 사진만 있는 신고, 여러 위험이 섞인 신고) 맞추고, 원인별(자료 없음 / 말이 달라 못 찾음 / 찾았으나 잘못 인용)로 해결한 뒤 다시 돌려 다른 사례가 나빠지지 않았는지 확인한다.

1. **언어 괴리**: 담당자가 유해요인을 적는 자연어와 근거(법령·기준·KOSHA·SIF)에 쓰인 용어 사이의 차이로 근거를 못 찾는 경우를 찾아 줄인다.
2. **빠진 자료**: 사례에 맞는 근거가 저장소에 없는 분야를 찾아 Supabase에 보완한다.

## 2-1. 근거 검색 방식 (2026-10-31 합의)

AI가 근거자료를 찾는 일반적인 방식을 따른다. 시뮬레이션 사례마다 관련어를 하나씩 넣어 점수를 맞추는 방식은 쓰지 않는다.

1. **검색어 바꾸기**: AI가 담당자 문장을 일상어와 법령 용어 검색어로 바꾼다.
2. **후보 넓게 찾기**: 단어 검색과 의미 검색으로 후보를 넓게 모은다.
3. **골라내기(재순위)**: AI가 후보 조문을 읽고 그 사례에 실제로 해당하는 것만 이유와 함께 고른다. 의미 검색은 엉뚱한 후보도 가져온다고 전제하고, 여기서 걸러낸다.
4. **초안**: 골라낸 근거만 인용해 초안을 쓴다.
5. **재검토**: 초안이 근거와 맞는지 다시 확인한다.

- **목표 방식은 "단어 + 의미 + 골라내기"**이다. 시뮬레이션은 셋 중 하나를 고르는 시합이 아니라, 이 방식이 우리 자료에서 실제로 맞는지 확인하는 채점표다.
- 비교 대상은 세 가지다.
  - 기준점: 단어 검색만(현재 운영 방식)
  - 참고: 단어 + 의미(골라내기 없음)
  - 목표: 단어 + 의미 + 골라내기
- 채점은 **실제 초안까지** 만들어서 한다. 맞는 인용 수, 엉뚱한 인용 수, 골라내기가 버린 정답 조문 수를 센다.
- 목표 방식이 기준점보다 맞는 인용이 많고 엉뚱한 인용이 늘지 않을 때만 운영에 켠다. 결과가 나쁘면 다른 방식으로 바꾸지 않고 원인을 찾아 고친다. 예: 골라내기 지시문, 후보 수, 남길 개수.
- 운영에서는 정해진 방식 하나만 쓴다. 정답이 없는 실제 신고에서는 여러 방식을 돌려 점수로 고를 수 없다. 자료를 추가하거나 법령이 개정되면 시뮬레이션을 다시 돌려 그 방식이 여전히 좋은지 확인한다.
- 담당자 표현을 법령 용어로 잇는 연결표는 보조로만 쓴다. 조문이 아니라 **법령 단어**로 연결하고, 의미 검색과 골라내기로도 계속 놓치는 표현에만 쓴다. 연결표를 만들 때 쓰지 않은 새 사례로 다시 확인한다.
- **자료 보완은 산업안전보건 법령 체계를 기준으로 한다.** "자료 없음"은 어느 단계가 비었는지로 분류하고, 그 단계의 공식 원문을 찾아 SQL로 보완한다.
  - 법률·시행령·시행규칙
  - 안전보건규칙·취업제한규칙
  - 행정규칙: 고시·예규·훈령
  - 공단 지도·권고: 기술상의 지침, 작업환경표준, KOSHA GUIDE
  - 소방·전기·건축·승강기·가스 등 다른 법령도 같은 방식(법 → 시행령 → 시행규칙 → 고시·기준)으로 본다.
- **이 작업의 목적 두 가지는 잊지 않는다.**
  - ① 의미 검색을 포함한 근거 검색의 정확도를 높인다(언어 괴리 해소).
  - ② 보완할 자료를 찾아 Supabase에 추가한다.

## 2-2. 중심 틀: RAG 표준 단계와 검증 순서 (2026-11-01 합의)

안심ON의 AI 초안은 RAG(검색 증강 생성) 표준 구조를 따른다. 새 아이디어가 나오면 먼저 아래 표의 어느 단계인지 정하고, 그 단계의 지표로만 판단한다. 한 번에 한 가지만 바꾸고, 처음 보는 사례로 검증한다.

| 단계 | 하는 일 | 원칙 | 지표 |
|---|---|---|---|
| ① 입력 이해 | 담당자 문장을 해석하고 검색어를 만든다 | 원문 표현은 유지하고 법령 용어 검색어를 덧붙인다. 일반어·흔한 말은 문장 맥락으로 바꾼다. AI가 이해한 위험을 화면에 드러낸다. 질문은 해석 자체가 불가능할 때만 한다 | 법령 용어 포함률, 질문 비율(20% 이하) |
| ② 후보 검색 | 단어 + 의미 검색으로 후보를 넓게 모은다 | 품질의 상한이다. 의미 검색은 담당자 원문으로 해서 AI 해석을 견제한다 | 정답이 후보 10개 안에 드는 비율 **90% 이상** |
| ③ 재순위 | AI가 후보를 읽고 상위만 남긴다 | 엉뚱한 후보를 여기서 거른다 | 상위 4개(법령 2 + 지침 2) 안에 정답 **70% 이상** |
| ④ 초안 | 남은 근거만으로 초안을 쓰고 인용한다 | 근거에 없는 내용은 쓰지 않는다 | 인용 중 엉뚱한 비율 |
| ⑤ 자동 검증 | 문장마다 인용 근거로 뒷받침되는지 본다 | 뒷받침 안 되는 문장만 표시하거나 뺀다. 인용을 통째로 버리지 않는다 | 검증 후 남은 정답 인용 비율 |
| ⑥ 사람 확인 | 초안·출처·AI 해석을 보여주고 담당자가 고르고 고친다 | 기본은 초안 하나. 다른 해석은 대책이 달라질 때만 함께 보여준다. 맥락을 적어 다시 만들면 검색부터 다시 한다. 수동 작성은 항상 가능하다 | (시범운영) 그대로 받아들인 비율·수정 비율 |
| ⑦ 평가 | 고정된 시험지로 단계별로 잰다 | 정답 기준은 "기대 근거 또는 판정 타당"으로 센다 | 위 지표 |

- 검증 순서: **② → ③ → ⑤ → ⑥**. 앞 단계 목표를 채우기 전에는 뒤 단계를 튜닝하지 않는다.
- ②·③은 초안 없이 검색만 다시 재서(replay) 비용을 아낀다. 고칠 때마다 처음 보는 담당자 말투 사례를 새로 만들어 검증한다.
- 빠진 자료는 시뮬레이션이 끝난 뒤 법령 체계 단계별로 한 번에 보완한다.

## 3. 시뮬레이션 작성 규칙

- 사례 문장은 **담당자 말투**로 쓴다. 짧은 구어체·줄임말·오탈자를 허용하고 법령 용어를 넣지 않는다(예: "택배 쌓아둔거 넘어질라함").
- 검색어는 사람이 정하지 않는다. 운영과 같이 **AI가 담당자 문장에서 뽑게** 한다(운영 「검색 정확도 점검」에서 측정).
- **기대 근거는 저장소와 무관하게** 정한다. 먼저 "어떤 종류의 기준이 답해야 하는가"를 정하고, 그다음 저장소에 있는지 확인한다.
- 결과는 두 갈래로 나눈다. **자료 없음** → 추가할 자료 목록. **자료는 있는데 못 찾음** → 담당자 표현↔법령 표현 대응 목록(검색어 지침·의미 검색으로 보완).
- 업무 구역(접수·발착·집배실·시설물·운송·사무후생·공사도급·비상)별로 결과를 낸다.

## 4. 진행 방식 (사용자 합의)

**원칙: 모든 작업은 에이전트가 끝까지 한다. 사용자는 전 과정이 끝난 뒤 제대로 했는지 검토만 한다.** 중간에 사용자에게 실행·확인·선택을 넘기지 않는다. 판단이 필요한 선택은 합리적인 기본값으로 진행하고 보고에 근거를 남긴다.

- 한국어로 답한다. 변경은 `claude/dreamy-feynman-3jnbrc` 브랜치에서 하고, `npm test` 통과 후 PR을 만들어 squash 병합한다.
- **Supabase**: 이 환경에 `SUPABASE_DB_URL`(PostgreSQL 연결 문자열)이 있고 해당 DB 호스트가 허용되어 있으면 SQL 적재·마이그레이션·적재 확인을 에이전트가 직접 실행하고 `supabase/loaded-sources.json`도 바로 갱신한다. 없을 때만 300KB 이하 SQL 파일을 `SendUserFile`(display `render`)로 보내고, 무엇이 막혔는지 함께 알린다.
- **AI 검색어·의미 검색 시뮬레이션**: `OPENAI_API_KEY`가 있고 `api.openai.com`이 허용되어 있으면 실제 AI 흐름으로 로컬에서 직접 돌린다. 없으면 운영 「검색 정확도 점검」에서 돌도록 코드를 준비하고 그 한계를 보고한다.
- **운영 확인**: 운영 주소(`ansimon-test-production.up.railway.app`)에 접근할 수 있으면 배포 반영을 직접 확인한다. 접근할 수 없으면 확인하지 못했다고 보고한다.
- 비밀번호·키·연결 문자열은 대화로 받지 않는다. 환경 설정(네트워크 비밀값 또는 환경변수)으로만 받는다.
- `local-import/`는 git에 없다. 적재한 자료의 버전은 `supabase/loaded-sources.json`에 기록한다.
- 그림으로만 된 PDF·별표는 자동 OCR로 넣지 않고 화면을 보고 옮겨 적으며 "원문 확인" 안내를 붙인다.
- 확인하지 않은 것(운영 반영, 실기기 설치, 실제 AI 응답, Supabase 적재)은 완료라고 말하지 않는다.
- 단계가 끝나면 `docs/dev-history.md`(개발 과정 압축 기록)에 한 일·결정·틀린 것과 해결을 한두 줄 덧붙인다. 보고 자료와 다른 앱 개발의 참고로 쓴다.
